# 사업자 이전 체크리스트 — 실글패스(kptest.cloud)

작성 2026-08-27. 11월 말 현 사업자(만물아들 · 이선호) 폐업 후 서비스를 어머니 사업자로 넘길 때
따라갈 순서표다. 저장소를 직접 조사해서 쓴 것이므로, 그사이 코드가 바뀌면 다시 확인해야 한다.

## 0. 한눈에 보기

- 코드에서 고칠 파일은 사실상 **4개** — 사업자 정보 파일 1개 + 하드코딩 예외 3곳(1장).
- 새로 발급받을 키는 **포트원 관련 5개**. 나머지 환경변수는 대부분 그대로 둔다(3장).
- 가장 오래 걸리는 건 코드가 아니라 **새 사업자 명의의 포트원 상점 개설과 PG 심사**(이니시스 ·
  카카오페이)다. 실글패스 처음 열 때 카카오페이 심사가 오래 걸렸으니, 폐업일보다 훨씬 먼저 시작한다.
- 예전 결제의 환불 · 조회가 사업자 변경 후 어떻게 되는지는 **코드만 봐서는 알 수 없다** —
  포트원 · 가맹점센터에 확인할 질문으로 정리해 뒀다(6장). 지어내지 않았다.

## 2. 결제(포트원) — 키가 전부 새로 발급된다

**왜 필요한가**: 포트원 상점과 PG(이니시스 · 카카오페이) 계약은 사업자등록번호에 묶여 있다.
사업자가 바뀌면 상점 · 채널 · 키가 전부 새 것이 된다. (같은 상점을 유지한 채 사업자만 바꿔 주는
절차가 있는지는 포트원에 확인 — 6장.)

코드가 쓰는 포트원 값은 5개고, 전부 Vercel 환경변수다:

| 환경변수 | 무엇 | 쓰는 곳(조사 확인) |
| --- | --- | --- |
| `NEXT_PUBLIC_PORTONE_STORE_ID` | 상점 ID | 결제창(`src/components/subscribe/PaymentButton.tsx`), 관리자 결제 화면 |
| `NEXT_PUBLIC_PORTONE_CHANNEL_KEY` | 카드(이니시스) 채널키 | 결제창 |
| `NEXT_PUBLIC_PORTONE_CHANNEL_KEY_KAKAOPAY` | 카카오페이 채널키 | 결제창 — 이 값이 없으면 카카오페이 버튼이 자동으로 '준비중'이 된다 |
| `PORTONE_API_SECRET` | 서버 조회 비밀키 | 결제 검증(`src/lib/payment.ts`), 관리자 결제 화면, 매출 · 환불 대사 스크립트 6개(`scripts/`) |
| `PORTONE_WEBHOOK_SECRET` | 웹훅 서명 비밀키 | `src/app/api/portone/webhook/route.ts` |

환경변수 외에 **포트원 콘솔에서** 할 일:

- 새 상점에 웹훅 URL `https://kptest.cloud/api/portone/webhook` 을 등록하고,
  **'Transaction.Cancelled'(결제 취소) 이벤트도 켠다.** 안 켜면 환불을 해 줘도 이용권이
  자동 회수되지 않는다(코드 주석에 명시된 운영 요구사항).
- 카카오페이는 이니시스와 **별개 계약**이라 채널이 따로 생기고 심사도 따로다. 실글패스 첫 개설
  때 시간이 걸렸던 부분이므로 가장 먼저 신청한다. 심사 기간은 포트원이 안내하는 값을 따른다(여기서 단정하지 않음).

## 3. 환경변수 — 바꿀 것 / 그대로 둘 것 / 명의를 확인할 것

코드 전체의 `process.env` 사용처를 훑어서 가른 결과다.

**반드시 새로 발급(사업자에 묶임):**

- 포트원 5개 (2장 표)

**그대로 둬도 됨(사업자와 무관):**

- `NEXT_PUBLIC_SUPABASE_URL` · `NEXT_PUBLIC_SUPABASE_ANON_KEY` · `SUPABASE_SERVICE_ROLE_KEY` —
  데이터베이스. 회원 · 문항 · 결제 기록이 전부 여기 있고, 그대로 이어진다.
- `ADMIN_EMAILS` — 관리자 로그인 이메일 목록. 운영자가 같으면 그대로.
- `TELEGRAM_BOT_TOKEN` · `TELEGRAM_CHAT_ID` — 운영 알림(결제 실패 · 오류 신고 등).
- `CRON_SECRET` — 구독자 리포트 자동 실행 보호용.
- `GOOGLE_SITE_VERIFICATION`, 검사 스크립트용 값들(`*_BASE`, `SHOOT_*` 등) — 서비스 운영과 무관.

**키는 그대로 돌아가지만, 결제 명의를 확인해야 하는 것:**

- `ANTHROPIC_API_KEY` — AI 채점 비용이 청구되는 계정. 폐업 후 이 비용을 누가 내는지에 따라
  어머니 명의 계정의 새 키로 갈아타는 게 맞을 수 있다. (별도 사이트 kbspass 설계에서도 "사업자가
  다르면 비용 귀속도 다르다"는 이유로 키를 나눠 쓰지 않기로 했다 — 같은 원칙.)
- `NEXT_PUBLIC_GA_ID` · `NEXT_PUBLIC_CLARITY_ID` — 구글 애널리틱스 · 클래리티. 계정 소유만 정리하면 값은 그대로.
- **코드 밖이라 이 저장소에서 안 보이는 것**: Vercel(호스팅) · Supabase(DB) · 도메인(kptest.cloud)
  요금이 결제되는 카드. 폐업하는 사업자 카드에 물려 있으면 갱신 실패로 서비스가 멈출 수 있다.
  각 서비스의 결제 설정 화면에서 직접 확인할 것.

## 4. 결제 데이터의 연속성 (가장 조심할 부분)

코드에서 확인한 구조:

- 결제 1건 = `subscriptions` 테이블 1행. `order_id` 칼럼에 포트원 주문번호(paymentId,
  `sub-…` 형식)가 중복 불가(UNIQUE)로 저장되고, `payment_key`에 PG 거래번호가 저장된다
  (`src/lib/payment.ts`, `supabase/migrations/004_subscriptions.sql`).
- 서버는 결제 검증 · 환불 대사 때마다 이 `order_id`로 포트원 API를 조회한다. 그 열쇠가
  `PORTONE_API_SECRET`이다.
- 회원이 탈퇴해도 결제 기록 행은 남긴다(전자상거래법 5년 보존 취지 — `supabase/migrations/036_keep_payment_records.sql`).

**우려되는 지점**: `PORTONE_API_SECRET`을 새 상점 것으로 바꾸는 순간, 옛 상점에서 일어난 결제는
새 키로 조회되지 않을 가능성이 높다(코드는 조회 실패를 '그런 주문 없음'으로 처리한다). 그러면 —

- 관리자 결제 화면과 매출 대사 스크립트에서 예전 결제가 안 보이게 되고,
- 예전 결제 고객이 환불을 요청했을 때, 이 시스템의 자동 회수(환불 웹훅)가 옛 상점 몫으로는 들어오지 않는다.

**이건 저장소만 봐서는 답이 안 나온다.** 6장의 질문을 포트원 · 가맹점센터에 미리 확인하고,
답이 오기 전에는 **옛 상점 콘솔 접근 권한을 없애지 말 것.**

다행인 점(코드로 확인된 사실): 이용권은 5,500원 **1회 결제 · 30일 이용권이고 자동결제가 없다.**
그래서 이전일 이후 옛 상점으로 새 결제가 생길 일이 없고, 이전 시점에 살아 있는 이용권은
직전 30일 안에 결제된 것뿐이다. '옛 상점 환불'을 신경 쓸 대상이 그만큼으로 한정된다.

## 5. 이전 당일 순서 (제안)

### 미리 (폐업일 한참 전부터)

1. **포트원 새 상점 개설 + 이니시스 · 카카오페이 심사 신청** — 심사가 끝나야 당일 작업이 가능하다.
   심사 중에도 기존 결제는 기존대로 돌아간다. *(왜: 심사 기간이 우리 손에 없다. 제일 먼저.)*
2. 어머니 명의 통신판매업 신고번호 확보 — kbspass 준비로 이미 돼 있다면 번호만 확인.
   *(왜: 사이트 표시의무 + PG 심사 요건.)*
3. 1장의 새 사업자 정보 값 확정(주소 · 연락처 · 개인정보책임자 포함). *(왜: 당일 코드 수정이 5분에 끝나게.)*
4. 6장의 질문들을 포트원 · 가맹점센터 · 세무사에 확인. *(왜: 답에 따라 당일 순서가 달라질 수 있다.)*
5. 3장의 '명의 확인' 항목(Vercel · Supabase · 도메인 결제 카드, Anthropic 계정) 정리.

### 당일 (결제가 적은 시간대 권장, 예: 새벽)

1. **(권장) 결제를 잠깐 닫는다** — Vercel에서 `NEXT_PUBLIC_PORTONE_CHANNEL_KEY`와
   `NEXT_PUBLIC_PORTONE_CHANNEL_KEY_KAKAOPAY`를 지우고 재배포. 코드가 이 상황을 안전하게
   처리하도록 이미 만들어져 있다: 카드는 "결제 설정이 준비 중입니다" 안내, 카카오페이 버튼은
   '준비중' 표시. **닫히는 건 새 결제뿐이고, 이미 결제한 사람의 이용권과 사이트 이용은 그대로다.**
   *(왜: 갈아타는 도중에 옛 사업자 상점으로 결제가 들어오는 걸 막는다.)*
2. 개발자 작업: `src/lib/businessInfo.ts` + 하드코딩 3곳(1장)을 새 사업자 정보로 수정하고 배포.
3. Vercel 환경변수에서 포트원 5개를 새 상점 값으로 넣고 재배포 → 결제가 자동으로 다시 열린다.
   *(왜: 코드는 키가 있으면 열고 없으면 닫게 돼 있어서, 별도 스위치가 필요 없다.)*
4. 포트원 새 상점 콘솔에서 웹훅 URL 등록 + Transaction.Cancelled 켜기(2장).
5. **검증 결제**: 실제로 5,500원 결제 1건 → 이용권이 발급되는지 확인 → 포트원 콘솔에서 그 건을
   환불 → 이용권이 자동 회수되는지, 텔레그램 알림이 오는지 확인.
   *(왜: 발급 · 회수 양방향이 다 돼야 웹훅 설정이 맞는 것이다.)*
6. 관리자 결제 화면(`/admin/payments`)과 환불 대사(`npm run audit:refunds`)가 새 키로 도는지 확인.
   예전 결제가 안 보이는 건 4장에서 예상한 일이므로, 옛 상점 콘솔로 보완한다.
7. 푸터 · 이용약관 · 개인정보처리방침 · 환불정책 · 고객센터에 새 사업자 정보가 떴는지 눈으로 확인.

**결제가 닫혀 있는 구간은 1→3 사이다.** 심사가 미리 끝나 있으면 재배포 두 번이라 수십 분이면
끝난다. 사이트 자체(시험 · 채점 · 기존 이용권)는 이 구간에도 정상 동작한다.

## 6. 열어 둔 질문 — 여기서 답을 지어내지 않았다

**포트원 고객센터에:**

- 사업자 변경 시 기존 상점을 유지한 채 사업자 정보만 바꿀 수 있나, 아니면 새 상점을 만들어야 하나?
- 새 상점이라면: 옛 상점의 결제 내역 조회(콘솔 · API)는 폐업 후 언제까지 가능한가?
- 옛 상점에서 결제된 건의 **환불**은 폐업 후 누가 · 어떤 경로로 처리하나?

**이니시스 · 카카오페이 가맹점센터에:**

- 가맹 해지(폐업) 후 기존 결제 건의 환불 처리 경로와 기한.
- 미정산 잔액이 있으면 어떻게 지급되는가.

**세무사에:**

- 폐업일 전후 매출 귀속과 부가세 신고. 이용권 기간이 폐업일에 걸쳐 있는 결제의 처리.
- 사업 양도 · 양수로 볼지, 그에 따른 신고 절차.

**개인정보(전문가 또는 개인정보포털에):**

- 서비스가 다른 사업자에게 넘어가면 개인정보 처리자가 바뀐다. 이용자 고지가 필요한지,
  개인정보처리방침을 언제 어떻게 개정해야 하는지. (이 저장소로는 알 수 없어 절차를 적지 않았다.)

**직접 확인:**

- Vercel · Supabase · 도메인 요금 결제 카드 명의(3장).
- Anthropic(AI 채점) 비용 계정을 새로 팔지(3장).
